## 2026-07-09 Reusable Workflow Package Manager Selection

- Status: Accepted
- Topics: reusable-workflows, package-managers, pnpm, compatibility
- Refs: .github/workflows/verify.yml, .github/workflows/deploy-pages.yml, docs/workflow-release.md
- Decision: Keep workflow release v1 npm-compatible while adding lockfile-based `package-manager: auto` support for pnpm, explicit `package-manager` overrides, and a `pnpm-version` input. Install pnpm with `pnpm/action-setup` only when the resolved package manager is pnpm.
- Rationale: Existing portfolio consumers are npm lockfile projects using `@v1`, so npm defaults must keep working. Lockfile detection keeps wrappers thin for new pnpm consumers, and explicit pnpm setup avoids depending on runner-bundled Corepack behavior or package-manager metadata that may change across pnpm versions.
- Alternatives: Make v1 pnpm-only; require every consumer to pass a package manager; rely on Corepack; extract the shared setup into a separate local action or composite workflow layer.

## 2026-07-09 Version Consumer Workflow Refs

- Status: Accepted
- Topics: reusable-workflows, consumer-compatibility, docs
- Refs: README.md, docs/consumer-standard.md, docs/examples/, docs/workflow-release.md, scripts/release-workflows.mjs
- Decision: Document consumer workflow wrappers with floating major tags such as `@v1`, backed by immutable `vX.Y.Z` workflow release tags.
- Rationale: Reusable workflow changes can alter install, cache, Pages, or package-manager behavior. Floating major tags let compatible fixes reach portfolio consumers without tracking `main`, while immutable tags and SHAs remain available for consumers that need frozen behavior.
- Alternatives: Keep `@main` for convenience; require every consumer to pin and bump immutable tags; publish separate branch-based workflow channels.

## 2026-06-29 Source Badge Icon Dependency

- Status: Accepted
- Topics: shared-web, badges, icons
- Refs: runtime/web/src/SourceBadge.tsx, runtime/web/src/LinkBadgeBase.tsx
- Decision: Add `SourceBadge` as a sibling wrapper to `BrandBadge` over an internal `LinkBadgeBase`, use `react-icons` for source-code icon presets, and auto-select the GitHub icon for `github.com` hrefs unless `iconName` is explicitly set.
- Rationale: `BrandBadge` and `SourceBadge` share rendering, sizing, styling, and unstyled behavior, but neither is conceptually the parent of the other. Existing consumer apps already use `react-icons`, and it provides both generic source-code icons and a GitHub icon without adding a second icon standard. GitHub is the expected source host for these portfolio apps, so detecting it in the default path keeps consumer markup cleaner while preserving explicit overrides.
- Alternatives: Make `SourceBadge` wrap `BrandBadge`; add `lucide-react`; paste inline SVG paths; require every consumer to pass its own icon; require `iconName="github"` on every GitHub source link.
